# Overview

Production setup: the app runs as an OTP release in Docker, behind Caddy
(which terminates TLS and fetches a Let's Encrypt certificate automatically).
State (the SQLite database, including participant photos) lives in a Docker
volume, so container rebuilds are lossless. The database sits in its own
`/data/db` mount and can optionally be kept on a host directory instead.

Relevant files:

| File | Purpose |
| ---- | ------- |
| `Dockerfile` / `.dockerignore` | Multi-stage build → OTP release (generated by `mix phx.gen.release --docker`, plus our `/data` tweak) |
| `.github/workflows/docker-publish.yml` | CI: builds the image and pushes it to `ghcr.io` on every push to `main` |
| `compose.yml` | `app` (pinned to the registry image) + `caddy` services, volumes, restart policy |
| `caddy/Caddyfile` | Reverse proxy + automatic HTTPS for your domain |
| `.env` (gitignored, create from `.env.example`) | `SECRET_KEY_BASE`, `PHX_HOST` |

# Publishing

Pushing to `main` triggers the **Publish Docker image** workflow, which
builds the production image and pushes it to GitHub Container Registry as
`ghcr.io/gregorybleiker/attendancetracker` (`latest`, `main`, and
`sha-<commit>` tags). Pull requests build the image without pushing, so
Dockerfile breakage is caught before merge. No secrets are needed for this:
the workflow authenticates with the automatic `GITHUB_TOKEN`.

The VPS therefore never builds — it just pulls. If the GitHub repo is
**private**, the package is private too, so log the VPS in once:

```bash
# Settings → Developer settings → Personal access tokens → Tokens (classic),
# with the `read:packages` scope
echo <token> | docker login ghcr.io -u <github-username> --password-stdin
```

Public repos need no login to pull.

# Prerequisites

- VPS with Ubuntu 24.04 (1 GB RAM is plenty), SSH access
- A domain with an `A` record pointing at the VPS, e.g. `attendance.example.com`
- Docker on the VPS: `curl -fsSL https://get.docker.com | sh`

# First deploy

1. **Point the proxy at your domain.** Edit `caddy/Caddyfile`, replacing
   `attendance.example.com` with your domain. Use the same value for
   `PHX_HOST` below.

2. **Create `.env`** (next to `compose.yml`, never committed):

   ```bash
   cp .env.example .env
   ```

   Fill in:
   - `SECRET_KEY_BASE` — generate locally with `mix phx.gen.secret`
   - `PHX_HOST` — your domain from step 1
   - `DATABASE_DIR` — *optional*. By default the SQLite database lives in the
     Docker-managed `db-data` volume (`/data/db/attendancetracker.db` inside
     the container). Set this to a host directory (e.g.
     `/srv/attendancetracker/db`) to bind-mount the database to the host
     instead, so you can inspect/back it up directly. The directory must exist
     and be writable by UID 65534 (the container's `nobody` user), e.g.
     `sudo mkdir -p /srv/attendancetracker/db && sudo chown 65534:65534 /srv/attendancetracker/db`.

3. **Get the code + `.env` onto the VPS**, e.g.:

   ```bash
   git clone <your-repo> attendancetracker && cd attendancetracker
   scp .env <user>@<vps-ip>:~/attendancetracker/.env
   ```

4. **Open the firewall** (ports 80/443 for Caddy, 22 for SSH):

   ```bash
   sudo ufw allow 22,80,443/tcp && sudo ufw enable
   ```

5. **Pull and start** (after pushing to `main` so the image is published —
   check the Actions tab first):

   ```bash
   docker compose pull
   docker compose up -d
   docker compose logs -f app   # watch it boot; Ctrl-C detaches
   ```

   (Building from source on the VPS with `docker compose up -d --build`
   works too, but pulling the CI-built image is faster and reproducible.)

   The `app` container runs `/app/bin/migrate && /app/bin/server`, so
   pending Ecto migrations apply automatically on every (re)start.

6. **Open `https://<your-domain>`**, log in with the default admin PIN
   `1234`, and **change the PIN under Admin immediately** (seeds don't run
   in production, so the default is active until you change it).

# Updating

```bash
git pull
docker compose pull
docker compose up -d
```

The `db-data` volume (or your `DATABASE_DIR` host directory) holds the
database — including participant photos — so updates don't touch your data.
Migrations run automatically on container start.

> **Upgrading from an older version (database moved to its own mount).** The
> SQLite database used to live at `/data/attendancetracker.db` inside the
> `app-data` volume; it now lives at `/data/db/attendancetracker.db` on a
> separate `db-data` volume. Before starting the new version, copy it over so
> the app doesn't come up with an empty database:
>
> ```bash
> docker run --rm \
>   -v attendancetracker_app-data:/old \
>   -v attendancetracker_db-data:/new \
>   alpine sh -c 'cp -a /old/attendancetracker.db* /new/'
> ```
>
> (Adjust the volume names with `docker volume ls` — compose prefixes them
> with the project directory name. Skip this if you use `DATABASE_DIR`, and
> just move the file into that host directory instead.)

See also [Backups](/backups.md) and [Troubleshooting](/troubleshooting.md).
